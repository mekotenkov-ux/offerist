# Карта всего сайта и объёмов

## Полнота решения, отдельно от полноты инвентаря

Сначала прочитай [внешний GAP и структурный fallback](external-gap.md). Own-only реестр, собственные когорты и объявление complete не задают внешний спрос. Для `site_gap.py` у `demand_review` добавлен явный `comparison`: `{mode: "search"|"structure", peers: [{domain, source_refs, complete}]}`. Домены отличны от клиента и объявлены `relevant:true` в `competitors`; `source_refs` ссылаются на сохранённые источники из `demand_review.sources` (список строк). `peer.complete` означает обработку всех страниц выбранного среза, а не всего рынка. В сопоставленных кластерах сохраняй `peer_urls` и `source_refs` на фактические строки того же источника, рядом с own URL/проверенным отсутствием, основанием и решением. Для XML укажи карту и проверенный peer URL; это не доказательство запросов и рангов. Helper проверяет связи метаданных; содержание оригиналов и достаточность среза проверяют автор и checker.

Без такого внешнего основания legacy-вход сохраняет расчёты, но `assessment.demand_review.complete` и `whole_site_gap_complete` остаются false. Незавершённая пагинация и `needs_business_answer` также не закрывают анализ. Поисковой режим может получить `complete_in_declared_scope`; структурный — только `structural_complete_in_declared_scope`, `structural_complete:true` и поисковой `complete:false`. Полный строгий workflow не принимает структурный результат за завершённый поисковой GAP; в автономном КП используй его полезные решения с явной границей. `landing_cohorts.py` выдаёт только `own_visibility_diagnostic`, `external_gap_assessed:false` и не подменяет этот контракт.

Выход helper assessment.action_review показывает проверенные/непроверенные страницы, долю и разбивку по типам. assessment.whole_site_gap_complete не становится true только от inventory.complete. Неизвестные действия видны в основном КП; это не keep и не доказательство отсутствия работ.

Дополнительный вход demand_review: complete boolean, scope, sources, clusters со стабильными уникальными id, status (covered, create_candidate, rejected, needs_business_answer, unknown), evidence и basis для проверенных. Здесь `covered` относится к подтверждённой применимости задачи спроса, а не только к наличию подходящего URL; неизвестное существенное условие услуги остаётся `needs_business_answer`/unknown с адресным вопросом, даже если на сайте есть путь обращения. Реестр описывает всю доступную базу после кластеризации, включая отсутствующие темы; это не только список уже выбранных новых URL. Полнота — заявленный scope, завершённые источники и отсутствие unknown, не доказательство всего рынка. Legacy-вход без реестра имеет status not_reported. Не сочиняй записи ради флага complete.

Ранги по полной доступной выгрузке дают mean и охват unique URL по типам; общий небольшой SERP набор можно оставить для дополнительного сравнения. Дата запроса, вес, порог и неопознанные/неранжирующиеся страницы сохраняются, не смешиваются с индексом и crawl.


## Охват и знаменатели

Единица инвентаря — уникальный проверенный canonical URL в заданной границе сайта. Сохраняй исходный URL, canonical, состояние (live/redirect/error/unknown), назначение интента `purpose`, тип страницы `page_type` и основание классификации. `purpose` — commercial/info/mixed/other/unknown; `page_type` — service/category/product/city/info и другие проверенные шаблоны. Эти оси нельзя подменять друг другом. Сведи crawl, sitemap, CMS, индексные и органические URL; не удаляй страницы из детализации только потому, что они не ранжируются. Для `inventory_complete` нужны обработанные все доступные страницы источников, сверка расхождений и явная граница обследования. Полнота crawl — это полнота обхода в его границах, не доказательство индексации.

Различай четыре числа: все обнаруженные канонические страницы сайта, индексные URL, уникальные URL с органическим ранжированием в заданном срезе и коммерческие/продуктовые посадочные. Покажи источник, дату, фильтры, метод дедупликации и неизвестные. `ranking URLs` из Keys.so/Ahrefs или иного сервиса — покрытие базы/порога; не называй его числом всех страниц. Если выгрузка содержит только topN, подпиши число как нижнюю границу видимого множества.

## Сопоставимость конкурентов

Для каждой пары клиент/конкурент укажи общее определение (`crawl`, `index`, `ranking_urls`), источник, дату/период, поисковую систему, регион, устройство, порог позиций, продуктовый/географический сегмент и правила canonical. Явно подтверди `relevant: true` по продукту, региону и аудитории; `false` и неизвестное исключаются из benchmark. Для типового benchmark нужны полные числа по всем типам (`type_counts_complete: true`) или полный инвентарь конкурента; неполную классификацию не превращай в нули. Считай абсолютную/относительную дельту только при одинаковом срезе; при нулевой базе относительная неизвестна. Сначала оцени релевантность типов страниц и таксономии. Конкурентные числа могут быть оценками провайдера — пометь это. Не усредняй несовместимые домены и не объявляй два сайта всем рынком.

## Ранги

Для GSC исходная единица — строка query × page × date/device/country (или иной описанный grain) с `position` и `impressions`. По одной выбранной когорте: `Σ(position × impressions) / Σ(impressions)`. Дедуплицируй исходные строки; не усредняй готовые средние URL или групп без их показов. Нулевые показы не дают позиции. GSC скрывает часть запросов и не подтверждает ранг каждого URL. Для SERP-съёмов считай отдельно `Σ(position × declared_weight) / Σ(weight)` по проверенным запросам; по умолчанию вес 1 на наблюдение, если он явно выбран. Укажи запросы, даты, гео, устройство, порог и правило веса. URL вне topN — цензурированное наблюдение, не позиция 0 или N+1; missing rank остаётся `null`. Среднее относится только к наблюдаемой когорте, при необходимости покажи долю URL с рангом. Междоменная дельта рангов допустима лишь по точным общим `query_id` при известном совпадении source/engine/region/device/period и объявленных method/segment/definition/threshold, единственной строке на запрос с каждой стороны и одинаковом весе пары. Иначе оставь дельту `null` с точной причиной; собственное и peer средние можно показать как описательные только с их раздельными scope/query IDs. Раздельно взвешенные средние разных сайтов не являются сравнительной дельтой. В клиентской строке типа охват позиций считай по наблюдаемым строкам и собственным URL именно этого типа; общесайтовый охват называй отдельно, отсутствие наблюдений не является позицией 0.

## Решение по работе

Для каждой существующей посадочной выбери `keep`, `optimize`, `rework`, `unknown`, один раз после canonical mapping. Доли считай от всех обследованных существующих URL, включая unknown. Отдельно запиши подтверждённые недостающие интенты: конкретная услуга/продукт и город (когда релевантно), коммерческая цель, спрос с источником/датой, конкурентные URL, проверка отсутствия подходящего клиентского URL и самостоятельности интента. Схожие кластеры объединяй; не превращай один интент в ряд городских страниц без уникальной ценности. Число утверждённых новых страниц следует из отдельных `landing_jobs` с решением `create`: несколько интентов могут требовать один job, а мотивированно отвергнутый интент не становится страницей. При неполной проверке показывай диапазон подтверждённых работ и неопределённую часть, а не фиктивный точный итог.

Сводная таблица для клиента — несколько строк по типам страниц и итог: текущие URL, среднее/медиана числа URL подтверждённо релевантных сопоставимых конкурентов и число таких конкурентов, наблюдаемый ранг клиента отдельно GSC/SERP с методом, подтверждённые `improve = optimize + rework` и отдельное число утверждённых `create` landing jobs, неизвестные, краткая причина. Отчёт `missing_intents.supported_count` и `type_gap_totals.supported_missing_intent_count` считает интенты, а `page_plan.approved_new_pages` — утверждённые уникальные задачи страниц; один будущий published page может покрывать несколько sourced task types с доказанной интеграцией. При открытом решении задач эти числа `null`, не ноль. `approved_published_page_target_all` — отдельная плановая проекция canonical inventory, а не сумма работ: полный наблюдаемый инвентарь плюс утверждённые создания недостаточны без решений о сохранении, снятии или слиянии каждого URL и новых уникальных canonical адресов. При неполном маршруте она `null`, а известные работы остаются. Утверждённые missing intents без типа входят в общий счёт, но не распределяются по типам. Конкурентные позиции показывай по каждому peer только при известном одинаковом scope; не усредняй средние peer. Машиночитаемая детализация хранит каждый URL, исходный evidence, каноникализацию, действие и каждый missing intent. План 3/6/12 месяцев берёт из этих работ последовательность и мощности, не обещает конкретный рост. `scripts/site_gap.py` рассчитывает проверяемые агрегаты; человек подтверждает классификацию и трудоёмкость.

Вход `python scripts/site_gap.py --input site-gap-input.json --out site-gap-report.json` — JSON. Обязательны `client_domain`, `inventory: {complete: boolean, scope, pages}`. `scope` содержит `definition, source, period, engine, region, device, segment` и при ranking URLs `rank_threshold`; определения и фильтры должны совпадать у сравниваемых доменов. `pages` — все проверенные уникальные живые `{url, canonical_url, purpose, page_type, action, basis}` в выбранном scope. Старый вход без `page_type` допустим, но тип станет `unknown`, а не выдуманным шаблоном. Исходные редиректы/ошибки храни отдельно как evidence, не считай живыми страницами. Дубли canonical вызывают ошибку до расчёта. Не подавай выборку как `complete: true`. Полный sitewide анализ допускает `complete: true` для структурного инвентаря при неизвестных рангах.

Для планового числа опубликованных canonical добавь `planned_url_dispositions` с одной строкой на каждый наблюдаемый URL: `{source_url, disposition, basis, source_ref, destination_url? | destination_landing_job_id?}`. Допустимы `retain_canonical`, `retire_410`, `redirect_or_merge`, `pending`; pending имеет `reason` и может ждать сохранённого источника. Решение о маршруте и `action: rework` — разные оси: снятие/слияние страницы может требовать оплачиваемой адресной работы, но не оставляет эту страницу в будущем URL-инвентаре. `redirect_or_merge` допускает другой явно сохраняемый наблюдаемый canonical или один утверждённый create job с отдельным новым адресом; несколько старых URL могут вести в один destination, который считается однажды. Если адрес job ещё неизвестен, укажи его ID и сохрани проекцию pending. Для каждого утверждённого `create` job укажи уникальный `proposed_url` клиента перед числовой проекцией. Отсутствующая legacy-строка или адрес нового job означает `projection_status: pending`, `approved_published_page_target_all: null`; `gross_observed_plus_approved_jobs` не подписывай будущим числом URL. Плановая проекция не является проверенным результатом после деплоя.

Необязательные `competitors` — `{domain, relevant, count, complete, scope, coverage, type_counts_complete, type_counts}`, где `count` относится к тому же определению страниц, а не к числу строк выгрузки. `type_counts` — объект `{service: N, category: M, ...}`; вместо него можно подать полный `pages: [{canonical_url, page_type}]`. Для типового сравнения обязательны `relevant: true`, `complete: true`, `type_counts_complete: true` и одинаковый scope. Отсутствующий тип при полной классификации означает 0; при неполной — неизвестно. Выход `type_gap` содержит среднее/медиану `competitor_count`, домены/число peer и явно показывает 0 peer как неизвестный benchmark. Старый вход без `relevant` разбирается, но peer не подтверждён и исключён из сравнений.

`count`, значения `type_counts`, `live_referring_domains` и `live_links` — неотрицательные целые числа (не boolean и не дробные); позиции и веса ранга могут быть дробными.

`rankings` содержит исходные `gsc: [{canonical_url, position, impressions, observation_id}]`, `serp: [{canonical_url, position, weight, observation_id}]`, `scope` и `coverage`; все строки каждого массива должны относиться к одной указанной когорте. `observation_id`, если задан, должен быть уникален в своём источнике, чтобы не удвоить вес. `position: null` — вне порога/неизвестно. Конкурент может дать `rankings: {scope, gsc, serp}`; для полного рангового handoff каждый наблюдаемый peer canonical URL должен иметь физический `page_type` в `competitors[].pages`. Если ранговая строка также содержит `page_type`, он должен совпасть с типом именно её URL; физический тип нельзя брать от другой страницы того же домена. `demand_type_id` запроса хранится отдельно и не меняет тип ранжирующейся страницы или знаменатель числа физических URL. Peer среднее по наблюдаемому срезу описательное; строгую парную дельту давай только при сопоставимых scope и общих query_id, иначе `null`. Числовой `rank_threshold` сравнивается как положительное конечное число; равные пороги не становятся unknown только из-за типа JSON. В сравнении рангов предпочтителен явно присутствующий `rank_threshold`: `0`, `false`, `null` и неизвестное значение не заменяй запасным `threshold`, а оставляй парную дельту `null` с неизвестным scope. Используй `threshold` только если ключ `rank_threshold` отсутствует; при двух разных корректных значениях сравнивай по предпочтительному ключу. Описательные средние наблюдений при этом сохраняются. `missing_intents` — `{id, page_type, supported, existing_urls_checked, independent, evidence, proposed_page}`; только три явных `true` и непустое evidence дают supported missing-intent ID, не утверждённую страницу. Если тип неизвестен, ID остаётся в общем числе и в `untyped_supported_ids`; `type_gap_totals` сверяет typed и untyped intent counts. `landing_jobs` перечисляет явные решения по source cluster/intent IDs. После полной reconciliation `page_plan` отдельно сообщает approved job IDs, число новых страниц по `published_type_id` и общий опубликованный target; до этого значения `null`. `links` — `{domain, provider, date, scope, complete, live_referring_domains, live_links}`, где `scope` — одинаковая строка/объект в одной базе; `complete` означает полноту доступного среза, а не всего веба. Любые отсутствующие метрики остаются `null`. Дополнительные поля evidence сохраняются в drilldown страниц и интентов. Итоговый файл содержит агрегаты и `drilldown`, но не принимает решений о цене или закупке ссылок.

При `research_findings.rank_rows` с доступными наблюдениями клиента или peer сначала вызови `workflow.py scaffold --node gap`: нерегистрируемый `rank_handoff_scaffold` перечисляет обе стороны без выбранных решений. В `complete` GAP каждую наблюдаемую собственную строку перенеси один раз в `rankings.serp`, а peer строку — в соответствующий `competitors[].rankings.serp` с тем же ID, query_id, canonical URL, position, весом, source_ref и срезом. Свяжи собственный URL с клиентским canonical inventory, peer URL — с физическим `competitors[].pages`; если тип ранговой строки указан, он должен совпасть с физической страницей. Либо внеси ID в `site_gap_input.rank_observation_exclusions: [{observation_id, reason, evidence_ref}]` с адресным сохранённым основанием: нерелевантный peer, иной срез, отозванная или непригодная строка. Несколько разных срезов не соединяй ради общего среднего. Частичный GAP может оставить неразобранный хвост явно pending, но включённая строка и в partial обязана быть верной; `complete` не может молча терять известные собственные или peer строки. Описательные средние получаются по своим сохранённым наблюдениям с отдельными n/охватом; сравнимые marginal cohorts не обязаны содержать те же запросы. Парная дельта требует точной общей когорты и известных граней среза, иначе остаётся `null`. Пустой `rank_rows` не является нулевой позицией и не доказывает отсутствия рангов вне объявленных проверенных источников.

Если исходная собственная ранжирующаяся URL отличается от текущей canonical страницы, сохрани исходный `research.rank_rows[].url` без замены. В `site_gap_input.rankings.serp[].canonical_url` укажи текущий проверенный canonical и добавь `own_rank_url_aliases` с observed/canonical URL и дескриптором точной строки сохранённого inventory/crawl JSON: `source_kind: saved_inventory|saved_crawl`, `source_ref`, `source_sha256`, `format: json_rows`, `rows_path`, `fields: {observed_url, canonical_url, observed_page_type}`. Поле `observed_page_type` в `fields` указывает имя колонки физического шаблона исходной страницы; его сохранённое значение повтори в `rankings.serp[].observed_page_type`. Валидатор сверяет единственную строку и отвергает подмену шаблона. Типовой ранг относится к физическому типу наблюдаемой ранжирующейся URL, а canonical inventory URL и его `page_type` остаются отдельной единицей подсчёта страниц. При расхождении шаблонов отчёт показывает ранг в строке наблюдаемого типа с нулём или другим числом canonical URL этого типа, не выдавая физическую страницу за вторую текущую canonical. Связь с сохранённой таблицей сама по себе не доказывает подлинность первичного crawl/HTML, актуальность canonical или сопоставимость запросов: проверь их отдельно. Семантический тип задачи спроса также остаётся отдельным полем.

## Ссылки

Считай отдельно уникальные **живые referring domains** и число живых ссылок в одном провайдере, дате и scope. Передавай релевантность, качество, типы, динамику и пересечения доменов, если доступны. Дельта доменов — ориентир для анализа, не заказ на покупку разницы; при несовместимом охвате оставь её неизвестной. Не смешивай Ahrefs с другим провайдером в одной разности.

`link_benchmarks` группирует только релевантных, полных и сопоставимых peer по одинаковым `provider/date/scope`. Для живых referring domains и ссылок отдельно показывает среднее/медиану peer, список и число peer с известным значением, клиентское число и наблюдаемую разницу; отсутствующее поле остаётся `null`, не нулём. Средние разных провайдеров или дат не объединяй, разницу не превращай в объём закупки.

Сохранённые `raw_referring_domains` и `raw_backlinks` не являются живыми метриками. Передавай каждую известную raw-строку с `source_row_id` и `source_ref`; `site_gap_report.raw_link_observations` сохраняет её и причину недопуска к сравнению. Для raw-сравнения в `links_assessment.raw_metric_basis[]` укажи `{metadata_ref, metadata_sha256, row_source_ref, source_row_ids, fields}`. `row_source_ref` находится в `evidence_files`; `fields` содержит `provider`, `date`, `target_grain` и хотя бы одно из `raw_referring_domains`/`raw_backlinks`, каждое как `{pointer, value}` с абсолютным JSON pointer в сохранённом metadata JSON. Значение должно дословно совпадать с файлом; ID перечисляют только строки, к которым эти определения относятся. Нет адресного определения метрики/зерна или строки другого среза — raw-значение видно, но не становится сравнением. Произвольный ярлык эквивалентности не доказывает одинаковый смысл. `raw_link_benchmarks` строится отдельно по метрике и точным provider/date/scope/сохранённым definition/grain: `client_value` — собственное число, `peer_count` — число уникальных релевантных полных peer-доменов с известным значением, `peer_values` — их адресные строки; ноль допустим, null не подменяется им. Peer-only однородный срез может дать описательное среднее без own-разницы. Живость, качество и объём закупки из raw-агрегата и донорской выборки не выводятся; частичная инвентаризация URL сама по себе не отменяет полного сохранённого domain-агрегата.

Для проверенного raw-агрегата объяви `links_assessment.raw_primary_sources[]`: `status: verified`, `source_ref`, `source_sha256`, `format: csv|json`, `row_source_ref` на нормализованный файл из `evidence_files`, `included_row_ids`, `excluded_rows`, `field_map`. CSV `field_map` сопоставляет `source_row_id`, `domain`, одну или обе raw-метрики и, если они есть в первоисточнике, `provider/date/scope` с именами колонок. JSON использует `rows_pointer` к массиву и относительные к строке JSON pointers в `field_map`. Проверка требует точного покрытия всех первичных ID: включённая строка совпадает с нормализованной по ID, домену, значениям и присутствующим полям идентичности; исключённая имеет `source_row_id`, причину и отдельный сохранённый `evidence_ref/evidence_sha256`. Пустой первичный массив с явным описанием допустим; пропуск известной строки или исправление значения только в нормализованном файле не проходят. `raw_source_refs` нормализованного файла перечисляет каждый первичный и вспомогательный файл; вспомогательный источник объявляется в `raw_supporting_sources[]` с `role: metadata|context`, `source_ref/source_sha256`. Если первичный формат ещё не разобран, оставь `status: unverified|unsupported` с сохранённым файлом, SHA и причиной: наблюдение остаётся видимым, но не входит в сравнение и не закрывает полный GAP. Определение метрики и зерна из `raw_metric_basis` проверяется отдельно; один лишь CSV/JSON счёт не доказывает сопоставимость, живость или качество.

Для `raw_link_benchmarks` сравнительный `scope` должен быть адресно сохранён: либо `field_map.scope` в первичных строках, либо `raw_metric_basis[].fields.scope: {pointer, value}` в metadata с применимостью к точным `source_row_ids`. Если есть оба, значения должны совпадать между источником, metadata и нормализованной строкой. `target_grain` — единица строки, не замена охвата среза. `workflow.py scaffold --node gap` показывает пустые альтернативы привязки, не утверждая их. Без source-backed scope числа остаются в `raw_link_observations` с причиной `scope_unbound`, но не дают сравнимое среднее/дельту и не подтверждают полный source-bound GAP; не придумывай scope ради статуса.

Для полного workflow GAP отдельно сохрани `link_snapshot` и передай в `site_gap_input` те же `links_assessment` и `links`. Минимальная форма оценки: `{status: "available"|"partial"|"unavailable", source_system, limitations, reason?, evidence_files: {"run-relative/source.json": "sha256"}}`. Файл доступного/частичного источника — сохранённый JSON с `links: [...]`; каждая нормализованная строка имеет `source_ref` на этот файл. `site_gap_input.links` должен точно повторять сохранённые строки. Workflow сверяет оба входа, SHA файлов и пересчитанный отчёт. Для `available` необходимы фактические неотрицательные целые метрики клиента и хотя бы одного подтверждённо релевантного конкурента в одном `provider/date/scope`, с `complete: true`; измеренный ноль допустим. Статус `partial`/`unavailable` требует точной причины и сохранённого evidence (например, записи об ограничении доступа), а неизвестные клиентские количества/дельты в `links_assessment` остаются `null`. Отсутствие `links_assessment`, пустое `available` и несовместимые строки не закрывают GAP. Этот статус описывает проверенность источника; он не предписывает покупать сервис или ссылки. Неполный источник и ограничения явно показывай в клиентском выводе.
