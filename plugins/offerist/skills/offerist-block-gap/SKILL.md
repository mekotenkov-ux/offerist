# Поблочный GAP всех типов

Получить от Продавца реестр типов, полный обнаруженный URL-инвентарь, семантические задачи, источники предложения клиента и релевантные peer страницы. Реестр типов — объединение текущих типов и типов, найденных по спросу/конкурентам; отсутствующий на нашем сайте тип не пропускается. Сначала проверить самостоятельную задачу типа, применимость к бизнесу и отличия от соседних типов. Число peer страниц само по себе не обосновывает новый тип или страницу.

Для каждого типа перечислить все обнаруженные существенные варианты шаблона и блоки, которые нужны для ответа на его интент. Сравнить смысл/полезность блоков, а не только наличие заголовка. Учитывать первый экран/предложение, состав и условия, процесс, цены или логику расчёта, доказательства, навигацию и контакт; информационная страница может требовать другого набора. Дополнительные нужные блоки извлекаются из задачи пользователя и peer, список открытый. Неприменимый блок имеет причину.

Проверять реальные страницы и содержимое каждого варианта; слабые URL первыми. Одинаковые шаблонные дефекты можно объединить, но распространение должно быть проверено на полном затронутом множестве/данных шаблона. Пара удобных примеров не доказывает покрытие других типов, вариантов или всех URL. Непроверенное остаётся unknown. Для отсутствующего нашего типа: собственные блоки absent/not_applicable с основанием инвентаря, конкурентные примеры и требования к созданию, не фиктивный скриншот нашей страницы.

Выход `block-gap.json` и краткая таблица: `type_id → variant_id → block_id → статус у нас → peer пример → конкретное изменение → affected_urls/landing_job_ids → масштаб → источник/дата → проверка результата`. Статусы `sufficient`, `weak`, `missing`, `not_applicable`, `unknown`. Каждый `affected_urls` должен быть действительным canonical URL этого типа и варианта с сохранённым own proof URL; каждый `landing_job_id` — утверждённой задачей `create`, чей `task_type_ids` содержит тип задания (её `published_type_id` может отличаться). Все утверждённые jobs получают variant и строки. Отвергнутые/покрытые существующим URL missing задачи сохраняют evidence-only `noncreate_job_ids` с точной причиной/источником, без work и billing; для покрытия нужен фактический URL и собственный saved proof. Для `weak`/`missing` обязательны `assessment_reason` с наблюдаемым своим состоянием или доказанным отсутствием, причиной разрыва по релевантному источнику, изменение, единица и приёмка. Для `sufficient`/`not_applicable` сохраняй `assessment_reason`, а `change`, `unit`, `acceptance` оставляй пустыми. Положительный достаточный блок тоже требует доказательства. Итог: покрытые/непроверенные типы, варианты, URL и блоки; структурные работы и потребности дизайна/разработки/контента без назначения стороны-исполнителя.

Единицы: общий шаблон — одна реализация + контроль затронутых URL; отдельное содержание — конкретные URL; новые посадки — уникальные независимые landing jobs. Не суммировать число блоков с количеством страниц. Передать Продавцу основания для optimize/rework/create, не самовольно менять коммерческие факты или цену. Все выбранные изменения должны попасть в стратегию и внедрение либо иметь явное решение об исключении.
