# Формат клиентского результата

Опорный документ — вложенный `assets/reference-proposal.docx`, синтетический пример КП для мебельного проекта example.org. Его структура и плотность служат ориентиром; новый клиент получает собственные факты и решения. Количество страниц определяется содержанием: не растягивай до 26 страниц и не ужимай аналитическое КП до формальной одностраничной продажи.

Пиши простым русским языком. Каждый аналитический блок ведёт к решению: что видно → на каких данных → какие страницы затронуты → что предлагаем → как проверим эффект. Число без периода, таблица без объяснения и обещание без основания не выполняют эту задачу.

## Порядок документа

| Блок | Что должно получить лицо, принимающее решение |
|---|---|
| Обложка | Клиент/сайт, агентство, SEO и выбранный GEO, дата. Один ясный заголовок, без чужих логотипов и фактов |
| Содержание и основной вывод | Краткая навигация; 3–5 предложений о текущей точке, главном резерве, предлагаемой работе и зависимости результата от внедрения |
| 1. Позиции и страницы входа | Сопоставимая таблица Яндекс/Google: объём мониторинга, TOP, видимость, органический трафик, страницы входа, источник и период. Динамика при наличии истории. Отдельно конкуренты, если есть сопоставимые данные |
| 2. Группы страниц и приоритеты | Определения «сильные / быстрый рост / слабые», численность и трафик без пересечений, независимая отметка бизнес-приоритета, примеры URL и следующее действие. Недостаточно данных — отдельный статус |
| 2.1. Семантическое покрытие | Ядро, мониторинг, фактическая связь запросов с URL. Покрытие и пробелы с понятным знаменателем; примеры кластеров, запросов и частотности с источником |
| 3. Точки роста | Разделённые таблицы «оптимизировать существующее» и «создать новое»: URL/интент, сигнал, бизнес-смысл, изменение, механизм, проверка. Выбери конкретные доказанные примеры, общий реестр приложи к расчётам |
| 3.1. Ссылки для Google | Какие целевые страницы могут выиграть, почему, какой тип внешнего размещения нужен и как выбирать площадки. Аудит и предложение будущей проверки различимы |
| 4. GEO, если выбран | Различие упоминания бренда, рекомендации и ссылки/цитирования; измеренная исходная точка или честно ожидающий измерения baseline; запросы пользователей, приоритетные страницы и внешние источники доверия |
| 5. Формула и прогноз | Карта рычагов роста простым языком; допустимый количественный расчёт, база, единицы, три сценария с явно указанными допущениями, лаг публикации и окна оценки. Трафик и обращения раздельно |
| 6. Работы и первый цикл | Какие работы влияют на каждый рычаг; конкретные входы, результат и критерии приёмки первого цикла. Далее — живая очередь по данным, эффекту и внедрению в рамках согласованного ресурса |
| 7. Жизненный цикл страницы | Выбор → диагностика → требования/контент → SEO/структура → согласование → внедрение → проверка публикации → измерение. Для каждого шага результат и ответственная сторона |
| 8. Смета и условия | Подтверждённая работа агентства, ресурс, внешние расходы, работы клиента/разработчика, необязательные опции/бонус. Период оплаты, итог и условия отдельно. Цена ближе к концу |
| 9. KPI и приёмка | Выполненные и внедрённые работы, эффект на опубликованных когортах, дата baseline и окно оценки. Условия бонуса только если согласованы; задержка внедрения переносит окно |
| 10. Релевантный опыт | Проверяемые кейсы: клиент/ниша, период, исходная точка, работа, результат, источник. Если кейсов нет — запросить их, не подставлять кейсы референса |
| 11. Аналитика и коммуникация | Кто принимает решения, внедряет и измеряет; содержимое регулярного отчёта, периодичность по условиям агентства, следующая встреча/первый шаг |
| Источники | Короткая клиентская таблица источников, периодов и существенных ограничений. Детальный технический журнал остаётся рядом с КП |

При отсутствии данных блок завершается честным статусом и конкретным действием для снятия неопределённости. Не раздувай такой блок общими обещаниями. Не выбранный GEO пропускается; согласованные пользователем локальные перестановки структуры допустимы.

## Типовые таблицы

- Страница: `URL/тип | поисковый сигнал и период | бизнес-приоритет | действие | ожидаемый механизм/проверка`.
- Кластер: `интент/пример запроса | спрос/источник | текущий URL/пробел | решение и основание`.
- Прогноз: `сценарий | допущения/объём | дополнительный месячный поток | база + прирост | накопленный прирост | условия`.
- Смета: `работа/ресурс | что получает клиент | сумма/период | кто оплачивает/внедряет`.

Широкий реестр со всеми техническими полями не помещай в основной текст. Не прячь важные финансовые условия и ограничения только в приложении.

## Визуальные блоки

Используй статичные диаграммы только при наличии соответствующих данных: динамика видимости двух систем, сравнение трафика, матрица SEO-группы × бизнес-приоритет, охват ядра мониторингом, сценарии прироста. Не создавай декоративные графики и не рисуй отсутствующие данные. У каждого блока название, период, единицы, легенда и короткий вывод. Таблица может заменить график, если так проще проверить числа.
