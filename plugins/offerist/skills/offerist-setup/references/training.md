# Обучение и границы данных «Оффериста»

## Два уровня памяти

`agency_id` — одно агентство (граница tenant); `run_id` — один клиентский запрос внутри него. Используй хранилище `--store` исполняемого комплекта «Оффериста»; по умолчанию это `.offerist` в рабочей папке. Не пиши в кэш установленного плагина. Профиль — `profile.json`, запуск создаёт `brief.md`, `proposal.md`, `evidence.json`, `run.json`; клиентская передача — отдельный `client-packet/`. Идентификаторы задавай без персональных данных. Если исполняемого комплекта нет, сохрани те же смысловые файлы в выбранной рабочей папке, не выдумывая статус машинной приёмки.

В профиле агентства живут только подтверждённые общие правила: услуги, компетенции, способ связывать цели клиента с решением, стиль, цены или метод расчёта, KPI, гарантии, инструменты, допустимые кейсы. В запуске живут дословные цели клиента, отдельная интерпретация, факты, гипотезы о препятствиях, исследование рынка, договорённости, варианты КП и замечания к нему. Ни один клиентский факт не становится правилом агентства автоматически. Новый клиент получает новый `run_id`; новое агентство — пустой `agency_id`, без копирования чужого профиля. Из старого КП можно учиться структуре и подаче, но названия, цифры, результаты и условия нужно подтверждать заново.

## Библиотека примеров результата работ

На настройке запроси несколько разных типовых задач, ТЗ, передаваемых результатов и отчётов, которые можно показать будущему клиенту. Храни карточки вне плагина, в `.offerist/agencies/<agency_id>/examples/`; `profile.json` содержит только `example_cards` — имена JSON-файлов относительно этой папки. Для отдельного проекта карточка имеет `scope: project` и точный `project_id`; общая карточка — `scope: agency`. Не смешивай карточки разных агентств.

Минимальная карточка: `id`, `type` (task/brief/deliverable/report), `title`, `task`, `deliverable`, `acceptance`, `goal_relevance`, `client_visible`, `scope`, `source_ref`, `evidence`, `status`, `claim_type: illustrative_deliverable`. Дополнительно укажи `project_id` для project, `permission_to_show` (`true` только при явном разрешении), `redaction` (`done`, `not_needed` либо `pending`) и при наличии `asset_path` к разрешённому обезличенному файлу относительно папки `examples/`. `source_ref` может быть лишь непрозрачным внутренним ID без пути к закрытому оригиналу; `evidence` служит внутренней прослеживаемости. Клиенту их не передают автоматически. `title` и `goal_relevance` формулируй без частных клиентских данных: они попадают в краткий индекс. `status: approved` означает проверенную карточку. Неизвестное разрешение или незавершённая редактура исключают карточку из клиентского подбора. Подпись к примеру должна объяснять передаваемый результат и критерий готовности; это иллюстрация работы, а не подтверждение бизнес-эффекта. Не копируй из старого примера клиентские факты, суммы, гарантии или обещания.

Закрытый эталон benchmark доступен только отдельному оценщику. В слепом тесте запрещены и оригинал, и производные: пересказанные приоритеты/условия клиента, извлечённые картинки, карточки примеров, старые КП и профили, обученные на эталоне. Отсутствие пути к PDF не устраняет перенос содержания. Для обычной работы разрешённая библиотека допустима; для независимого бенчмарка требуется отдельная проверка происхождения каждого входа. Не переименовывай источник, чтобы скрыть происхождение; неизвестное происхождение исключает материал из blind-пакета.

## Как учиться на примерах и замечаниях

Для каждого извлечённого правила запиши: формулировку, класс (`факт агентства`, `редакторское предпочтение`, `условие конкретного клиента`, `предположение`), источник и точный фрагмент, дату, статус (`предложено`, `подтверждено`, `отклонено`). Повторяемость в примерах не делает цену, гарантию или GEO-компетенцию подтверждённой. Противоречия показывай владельцу профиля; прежнее правило остаётся активным до решения.

Каждое замечание сохраняй как запись: `agency_id`, `run_id`, версия и хеш КП, кто дал отзыв, дословный смысл замечания, к какому месту относится, принятое исправление и исход повторной проверки. Совет для одного КП остаётся в запуске. Для устойчивого изменения профиля подготовь короткий diff «было → будет», основание и пробный фрагмент/КП; после явного подтверждения активируй новую версию, сохрани предыдущую для отката. В исполняемом комплекте обратная связь проходит через `feedback`, отмена — через `retire-rule`; вывод из примеров имеет статус `proposed`, а `active` требует явного указания пользователя. Отдельно фиксируй, какие запуски требуют обновления; не переписывай старые КП молча.

Пробный запуск должен быть настоящим: конкретный бриф → полное КП → независимый `offerist-client-review` на закрытом наборе видимых клиенту файлов → замечания → правка → повторная проверка. По умолчанию до трёх циклов исправления. Модельный вердикт подтверждает только результат независимого ревью этой версии. Итоговую оценку пользователя фиксируй отдельно; его отказ переоткрывает качество. При нерешённых блокерах сохрани их и статус `не готово`.

Не записывай ключи, токены, закрытую клиентскую переписку в общий профиль и не раскрывай их в КП. Если хранилище недоступно, оставь результат текущего запуска в явном выдаваемом файле и честно укажи, что постоянное обучение не сохранено.

Явное поручение пользователя сохранить правило уже считается подтверждением: отдельный approval-цикл не нужен. Область agency — выбранное агентство, project — данный проект, run — текущее КП. Новая задача читает context до работы. Из журнала feedback в `active_rules`/`proposed_rules` нового контекста переходят только `id`, `agency_id`, подходящие `project_id`/`run_id`, `scope`, `status`, обобщённые `rule`/`check` и `recorded_at`; `id` с датой позволяет найти полную запись для аудита. Дословный отзыв, `source`, примеры `before`/`after`, суммы, URL прежнего клиента, автор и результат повторной проверки остаются в файле события. Не включай клиентские детали в сам текст `rule`/`check`: они по назначению читаются в следующих подходящих запусках. Противоречивые гарантии нельзя одновременно активировать.
