# Память и исполняемые помощники

В `client-handoff.json` можно задать `type_labels`: карту известных `type_id` из принятого semantic map на читаемые названия для основных таблиц. Это оформление клиентского документа, без изменения аналитических источников. Подписи должны быть непустыми, однозначными, совпадать с уже заданными upstream-названиями и действительно присутствовать в связанных строках таблиц. Полнота типов и варианты по-прежнему проверяются по исходным ID.

Для первичного JSON с числом, периодом и фильтром прямо в корневом объекте numeric origin допускает явный `row_pointer: ""`. Его `value_pointer`, `period_pointer` и указатели `filter` должны выбирать прямые поля этого объекта. Пустой root pointer не позволяет объединять число и период разных вложенных строк; для них указывай точную строку обычным непустым pointer.

Если compact demand cluster не содержит `own_urls` и не связан с новой посадочной, адреса существующих страниц могут поступить из `query_decisions_ref` либо `source_ref` единственного совпадающего принятого GAP cluster. Этот JSON обязан быть закреплён SHA в `gap.consumed_sources`. Его `rows` покрывают каждую исходную фразу кластера ровно один раз (`query_id`, `phrase`, `cluster_id`, `disposition`, `reason`, `evidence_refs`, `target_urls`); решения совпадают с принятой картой, а адреса — с `page_allocations` того же типа. Явно заданный `own_urls` не подменяется этим путём.

Новые `init-run` создают schema_version=2 и scope.json. Для полного КП инициализируй [workflow](../../../docs/workflow.md), записывай результаты узлов и возобновляй только затронутые стадии. В run.json, scope.json и выходе intake должны совпадать agency_id, run_id, site, geo и geo_user_quote; чужой сайт/запуск или несогласованное решение GEO блокируют итог. `check` сверяет workflow-state по реальным файлам и требует content_scope_complete; одна положительная review.json не закрывает пропущенные анализы. Полный workflow `proposal` использует именно корневой `proposal.md`; его `client_packet` привязан к `packet-receipt.json`, точному SHA `client-packet/<revision>/manifest.json` и файлам пакета. Вход `client_review.review_receipt` — именно корневой `review.json`, а `candidate_sha256` равен SHA manifest. `check` сравнивает эти SHA, ревизию и reviewer/producer lineage между обоими контурами; чужой или устаревший пакет блокирует итог. Старый schema-1 запуск может иметь структурно валидную квитанцию, но получает предупреждение и content_scope_complete=false. Коммерческий статус и пользовательская приёмка остаются отдельными.

## Короткое общесайтовое КП

Основной формат — [стандарт B2B v4](standard-b2b.md) и [редактируемый шаблон](../assets/proposal-short.md). Итоговые таблицы и полный реестр страниц сохраняй отдельно: основной документ короткий, приложение содержит исходные расчёты. Для агрегатов используй scripts/site_gap.py из корня плагина: --input dataset.json --out gap-summary.json. Схема и ограничения — [page-map](../../offerist-gap/references/page-map.md). Скрипт считает введённые данные, не собирает сайт и не подтверждает их подлинность.

Новый run.json начинает с commercial_status: estimate_pending_human. В review.json сохраняй отдельный content_verdict: accept означает содержательное модельное заключение; verdict относится к готовности покупки. При человеческой смете и содержательно принятом пакете используй `content_verdict:accept`, `verdict:content_ready_price_pending`; это не выдаёт покупательскую или пользовательскую приёмку. `revise` остаётся для настоящих исправляемых дефектов. Поля ставки/суммы/оплаты оставляй заполняемыми человеком, не повторяй весь конвейер только ради этих полей. Локальные review/host JSON не доказывают независимый контекст: check всегда возвращает review_independence_verified:false и release_ready:false с отдельным требованием проверки хостом/оркестратором. Реальный вызов и его пакет проверяются по инструментам хоста; структурная квитанция сама по себе не заменяет этого.

Для SEO-аудита используй любые реально доступные источники с сохранённым файлом, датой и охватом. GSC URL Inspection не обязателен, если аудит обоснован другим путём; отсутствие GSC и его непроверенные состояния явно сохраняй. Для выполненной адресной проверки статус привязывается к точному URL запроса и ответу именно её источника. Изменение вложенного доказательства инвалидирует узел audit и его зависимых потребителей.

Для BAR полный охват означает решение по каждому типу и слабому URL. Реальные scored строки сохраняют input/report и повторный запуск bundled адаптера; `not_applicable` допустим только для доказанной непоисковой utility/legal/navigation функции либо отвергнутого нерелевантного semantic type, с типом/URL, intent, reason/basis и сохранёнными evidence файлами/SHA. N/A не получает метрик и отчёта, но остаётся в реестре и получает reasoned disposition стратегии. Нет peers/корпуса/ранжирования/времени для коммерческой или информационной посадочной — это blocker/partial, не N/A. Форма: [workflow](../../../docs/workflow.md) и [контракт анализа](analysis-contracts.md).

Python 3.10+, только стандартная библиотека. Путь к скрипту — `scripts/offerist.py` от корня плагина. Команды запускаются с полным путём к скрипту. `--store` — выбранное пользователем/агентом постоянное хранилище; по умолчанию `.offerist` в рабочей папке. В новом проекте найди существующий путь профиля или попроси переносимый профиль. Данные не пишутся в кэш установленного плагина: обновление не должно стереть обучение.

Отдельный [генератор графиков](../../offerist-charts/SKILL.md) `scripts/charts.py` использует Pillow. Он не обращается к API, сохраняет PNG/SVG и квитанцию исходных рядов. Для Метрики/GSC/Вебмастера используй эти графики и таблицы без снимков панелей. Общий барьер `screenshot:tool` снят; при `geo: yes` по-прежнему требуются реальные снимки `yandex`, `google`, `chatgpt` либо явное согласование отсутствующего GEO-снимка.

```text
python scripts/offerist.py --store /project/.offerist init-profile agency-id --name "Агентство"
python scripts/offerist.py --store /project/.offerist init-run agency-id run-id --site https://example.org --geo undecided
python scripts/offerist.py --store /project/.offerist context agency-id --run run-id
python scripts/offerist.py --store /project/.offerist feedback agency-id --input correction.json
python scripts/offerist.py --store /project/.offerist retire-rule agency-id rule-id --reason "заменено новым условием"
python scripts/offerist.py --store /project/.offerist packet agency-id run-id
python scripts/offerist.py --store /project/.offerist check agency-id run-id
python scripts/offerist.py calculate --input dataset.json
```

`profile.json` содержит критерии, KPI, гарантии, цены, кейсы, формат, инструменты и `example_cards` — список имён JSON-карточек в `.offerist/agencies/<agency_id>/examples/`; редактируй его по разговору и не заполняй неизвестное вымышленными значениями. `context` возвращает `profile`, текущий `run`, `active_rules`, `proposed_rules` и `examples_index`: только разрешённые карточки подходящей области с `id`, `type`, `title`, `goal_relevance`, `scope`, при необходимости `project_id` и `card_path`. Полное содержание карточек остаётся в файлах; seller читает только потенциально относящиеся к текущим целям, а окончательную релевантность решает по брифу. В индекс входят лишь `client_visible: true`, `permission_to_show: true`, `status: approved`, `claim_type: illustrative_deliverable` и `redaction: done|not_needed`. Индекс не выдаёт `source_ref`, `evidence` или `asset_path`; файлы приложений не копируются автоматически. Контракт карточки и границы эталона описаны в [правилах обучения](../../offerist-setup/references/training.md).

В каждом правиле из feedback разрешены только `id`, `agency_id`, применимые `project_id`/`run_id`, `scope`, `status`, обобщённые `rule` и `check`, `recorded_at`. Пара `id` + `recorded_at` указывает на запись происхождения в журнале; свободный текст `source` и материалы прежнего клиента в context не попадают. Формулируй `rule`/`check` без чужих URL, сумм и других частных фактов. `feedback` записывает отдельный полный файл события и reread-квитанцию; запись с `status=active` только для явного указания пользователя. Для выводов по референсам — `proposed`. Область `project` определяется точным `project_id`; `run` — `run_id`. Выведенные правила не меняют гарантии автоматически. Отмена — событие `retire-rule`; история сохраняется.

`init-run` создаёт brief.md, proposal.md, evidence.json, run.json. Заполни тексты. Seller дополнительно создаёт внутренний `examples-usage.json` с массивами `used` и `skipped`, каждый элемент — `id` и `reason`. `run.json`: `project_id`, явный `geo`, `seller_id` реального контекста, `criteria` (ID и текст), `quality_checks` (ID → pass/fail с reason), `exceptions` (criterion/evidence scope + user_quote + reason). Нельзя самому сочинять согласование ограничения. Профильные критерии скопируй в run при старте; актуальные дополнения пользователя учитывай тоже.

`evidence.json` — список карточек: `id`, `kind` (metric/screenshot/observation/example/chart), `source`, `captured_at`, `scope`, `observation`, `limitation`, `status` (observed/unavailable), для скриншота `path` внутри папки запуска, `inspected: true`, `surface` (tool/yandex/google/chatgpt), `comparison_id`, `sha256`. Screenshot с доступным файлом сам по себе не подтверждает правильность вывода — агент должен просмотреть изображение. Для `kind: chart` укажи `client_visible: true`, `status: observed`, `path` к PNG внутри запуска, действительный `sha256`, непустые публичные `source`, `captured_at` и `caption`. График — визуализация данных: для Метрики/GSC/Вебмастера это основной формат, без требования снимков панелей; он не считается скриншотом и не закрывает барьер реальных GEO-снимков. Для `kind: example` укажи `client_visible: true`, `status: observed`, `path` к разрешённой копии внутри запуска и `sha256`; допустимы `.md`, `.txt`, `.png`, `.jpg`, `.jpeg`, `.webp`, `.pdf`. `source` здесь только внутренний непрозрачный ID карточки. `observation` или `caption` описывает иллюстративный результат работ, а не подтверждённый бизнес-эффект. Не сохраняй токены, cookies и личные данные в evidence.

`packet` создаёт новую ревизию **только** в `client-packet/<revision>/`: `brief.md`, `proposal.md`, `attachments.json`, `attachments/` с выбранными клиентскими скриншотами, графиками, примерами и наблюдениями и `manifest.json` с хешами всех файлов. Для полного workflow до вызова `packet` подготовь в корне запуска `client-handoff.json` и `visible-appendix.md`; CLI копирует их в ревизию и включает в manifest. Первый файл связывает клиентские строки с подтверждёнными результатами анализа и работами, второй даёт читаемые карты типов/вариантов и поблочных решений, измерение обращений и поле релевантного кейса. `proposal.md` ссылается на вложенное `visible-appendix.md`; одного названия файла или ссылки на внутренний JSON недостаточно. Схема ниже и [workflow](../../../docs/workflow.md). Для `chart` он проверяет путь внутри запуска, PNG и SHA-256, копирует файл и переносит в `attachments.json` публичные `source`, `captured_at`, `caption`, относительный `path` и хеш. Для `example` он сверяет путь и SHA-256, копирует разрешённый файл, а в `attachments.json` переносит только `id`, `kind`, `observation`/`caption`, `status`, относительный `path` и хеш — без `source`, `source_ref` и другой внутренней прослеживаемости. Ссылки в КП должны указывать на фактический относительный путь из этого пакета; изменение КП требует новой ревизии. `packet-receipt.json` в корне запуска указывает путь ревизии и хеш manifest. Передай только каталог ревизии новому контексту. Изоляция обеспечивается вызовом хоста, а не самим Python; пакет минимизирует случайную передачу внутреннего контекста.

Для полного `.20` handoff добавь под корнем запуска только необходимые клиентские файлы `client-evidence/`: короткие таблицы исходных строк, отображаемые графики и копии native BAR reports/доказательств N/A. `packet` копирует ровно ссылки из `material_claims[].source_table_ref`, `visuals[].chart_ref` и `bar_summary[].report_ref|evidence_ref`, затем хеширует их в manifest. Не помещай туда секреты и не пересылай полную внутреннюю выгрузку без нужды. Видимая Markdown/HTML диаграмма с подписью нужна при пригодных данных; при отсутствии — видимая причина N/A.

Минимальная форма `client-handoff.json`: `schema_version:1`, `type_variants[]` (`type_id`, `variant_id`, `own_urls`, `peer_urls`, `rank_scope`, `rank_coverage`, `rank_positions`, `url_decisions`, `task_decision`, `intent_ids`, `basis`), `block_findings[]` (`source_id`, `type_id`, `variant_id`, `block_id`, `status`, `target_urls`, `landing_job_ids`, `disposition`, `action_id|null`, `reason`), `unique_works[]` (`action_id`, `unit`, `quantity`, `phase`, `acceptance`, `estimate_ref`), `measurement_plan`, `case_field`. `intent_ids` — все исходные интенты типа, **не** список доказанных пробелов; конкретные missing смотри в GAP. `type_variants` охватывает каждый вариант `block_register`; `block_findings` — каждый его assessed block, а выбранная работа ровно одна по action_id и связана с implementation/estimate. `sufficient` получает `no_action_required`, `not_applicable` — собственную причину; `unknown` не допускает полный block GAP и не маскируется как отсутствие работы. Строки обеих карт, измерения и кейса должны реально отображаться в `visible-appendix.md`. Не выводи приложению внутренние секреты или недоступные клиенту доказательства.

Для `.20` замени `schema_version` на `2` и добавь `material_claims[]`, `visuals[]`, `bar_summary[]` по [контракту workflow](../../../docs/workflow.md). Например, при неизвестной базе: `{"claim_id":"baseline","status":"unknown","visible_quote":"База обращений не подтверждена","value":null,"unit":"inquiries","period":"текущий","scope":"сайт","reason":"Нет подтверждённого регистра"}`. Наблюдаемое `12` требует файл вроде `client-evidence/visits.json` с адресуемыми строками, конкретные ID этих строк и вычисление; видимая таблица приложения кратко показывает источник, период и ограничение, но не сериализует внутренние словари в ячейки. Для `visuals` явно выбери встроенный проверенный график или мотивированное N/A. Для scored BAR оставь вывод с текущим native report, score факультативен; N/A сохраняет точную причину и proof. CLI проверяет сохранённые bytes/SHA и простую арифметику, человек проверяет внешнюю подлинность и полноту карты.

Для полного `.24` используй `client-handoff.schema_version:4` и [контракт клиентской передачи](analysis-contracts.md): сохрани прежние поля, `demand_decisions[]` по всем доступным raw query IDs, `source_rows[]` с доступными первичными строками спроса/ссылок, `material_proofs[]` по существенным положительным и выбранным block/audit утверждениям, полный `unique_works[]` по implementation actions и `main_tables` для фактических таблиц основного КП. В `material_proofs` одна строка на `(source_id,evidence_id)`: `source_ref`, `source_sha256`, `source_url`, `captured_at` (null, если неизвестна), `status:shown|unavailable`, `limitation`. Для `shown` добавь `packet_ref:client-evidence/...` и `mode:copy|excerpt`; excerpt должен быть дословным фрагментом сохранённого источника. Для `unavailable` оставь `packet_ref:null`, объясни `reason` и покажи `claim_limit` в приложении. Копируются только явно названные безопасные `packet_ref`; source ref не становится ссылкой на отсутствующий у клиента файл. Клиентская таблица работ показывает каждую единицу и приёмку, в том числе measurement-only.

`measurement_plan`: явный `outcome_unit` (`unique_confirmed_inquiry`, `confirmed_order`, `revenue` или `commercial_search_clicks`), `event_definition`, `source_status: available|unavailable`, соответствующий источнику `source_kind`, `source_ref` при доступном источнике, `period`, `dedup_rule`, `comparison_periods: [B3,B6,B12]`, `baseline: {status: known|unknown, value, period, source_ref, reason}`. Альтернативная обращениям первичная метрика требует `metric_rationale` по задаче клиента. Источники уникальных обращений: CRM/журнал звонков/проверенная форма; заказов: CRM/реестр заказов; выручки: бухгалтерия/реестр заказов; коммерческих поисковых кликов: GSC/Вебмастер/веб-аналитика с проверенным сегментом. Клик цели не считается уникальным обращением. Для неизвестной базы `value:null` и причина; для известной — неотрицательное измеренное количество, период и тот же источник, что у первичной метрики. `proxy.status: observed` требует реально наблюдённого числа и `source_ref`, `planned` — событие/единицу без источника и наблюдённого значения, `unavailable` — явную причину и оба значения `null`; каждый proxy содержит ограничение и `is_unique_inquiry:false`. Нельзя писать ноль вместо недоступных данных. `verification: {owner_role,method,cadence}` определяет, кто и как сверит результат; обязательной CRM нет. `company_case_pack.cases[]` помечает `fit_status: relevant_confirmed|illustrative_only`; без подтверждённо релевантного кейса требуется `human_case_field: {status:pending,label,reason}`, видимое клиенту.

Дополнение `.21`: новый план явно содержит `promised_segments: []` либо строки обещанной детализации. Строка `planned` имеет непустые `segment_id`, `capture` (где получить поле), `persist` (где хранить), `join` (как связать с подтверждённой записью), `unknown_bucket` (что делать при отсутствии связи), `test` (проверяемый сценарий), непустой список `dependencies` и булево `committed`. Строка `unavailable` содержит `segment_id`, `reason`, `committed:false` и не может оставаться обязательным результатом Б3/Б6/Б12. Для формы и звонка не предполагай одинаковую доступность посадочной: при заявленной общей детализации назови путь данных каждого канала или границу unknown. `client-handoff.measurement_plan` повторяет план, а видимая строка измерения показывает объявленные сегменты. Старые `.20` планы могут не иметь поля; структурная проверка валидирует объявленное, но не выводит полноту списка из свободного текста. Свежий Клиент проверяет это сопоставление.

Для `source_status:available` `source_ref` — путь к JSON receipt внутри run. Минимальная форма: `{status:"observed", unit, event_definition, period, dedup_rule, observed_value, source_kind, captured_at, scope, source_artifact_ref, source_artifact_sha256}`. Receipt сравнивается с планом и базой, отдельный сохранённый source artifact должен существовать, быть непустым и совпадать по SHA. Если источник существует, но базовый период ещё не измерен, `baseline.status:unknown` и receipt `status:"available_no_baseline", observed_value:null`; отсутствие первичного источника — `source_status:unavailable`, без фиктивного receipt. Для `proxy.status:observed` укажи его `source_kind`, `period`, `dedup_rule`, числовой `observed_value` и такой же receipt с `unit`/`event_definition` самого proxy. `planned`/`unavailable` продолжают работать с null source/value. Receipt и его source artifact входят в fingerprint `decision_map`; CLI сверяет сохранённые файлы и поля, но не может сам доказать, что внешний отчёт или ручная дедупликация подлинны.

Числовая семантика `.19`: известные `unique_confirmed_inquiry`, `confirmed_order`, `commercial_search_clicks` — неотрицательные **целые** количества; `revenue` — конечное неотрицательное число, дробная денежная сумма допустима. Для наблюдённого proxy `event_count`, `visit_count`, `click_count` также целые. Иная несчётная единица proxy (например, `ratio`, `average`, `duration_seconds`) требует `value_kind:"continuous"` и конечного неотрицательного числа; назвать `event_count` непрерывной величиной нельзя. То же правило действует на `observed_value` в receipt. `NaN`/`Infinity`, которые отдельные JSON-парсеры могут принять как расширение, запрещены в измерениях. Неизвестные/planned/unavailable значения остаются `null`, не нулём.

`estimate_sheet.lines[]`: `{estimate_ref, action_ids, unit, quantity, phase_quantities, basis}`. Каждый action из implementation назначен одной строке; её количество и разбивка по этапам равны сумме этих actions. `decision_map.decisions[].estimate_ref` обязан указывать на существующую строку со своим action; одинаковый `estimate_ref` допустим для группы действий одной единицы. Rates/sums/terms при `estimate_pending_human` остаются пустыми для человека.

Результат review.json: `verdict`, `content_verdict`, `reviewer_id`, `producer_id`, `context_id`, `producer_context_id`, `context_mode: fresh`, `independence_status: host_evidenced`, `candidate_sha256`, `proposal_sha256`, `packet_sha256`, `issues` (severity critical/major/minor, location, reason, fix), `criteria_results` (ID → pass/fail + reason). `candidate_sha256` и `packet_sha256` — один SHA фактически переданного manifest; `proposal_sha256` — SHA того же `proposal.md` внутри и вне пакета. Сохранённый отдельно `host_receipt` связывает те же ID/contexts/candidate, но сам по себе не доказывает независимость. Перед dispatch включи в клиентский brief согласованные `criteria` — только ID и текст, без `quality_checks` и иной самооценки продавца. Рецензент сохраняет эти ID и может добавить свои. IDs продавца и клиента — настоящие идентификаторы контекстов хоста: свой ID бери из данных хоста или `CODEX_THREAD_ID`; если его нет, оставь `pending_host`, не ищи собственный ID через общий список чатов или чтение других контекстов. Код проверяет согласованность записи, но не может доказать независимость модели или качество текста: это проверяет оркестратор по фактическому запуску.

`check` — структурный барьер: новый GEO-выбор, непустые материалы, критерии, отсутствие критических дефектов, актуальное слепое ревью, хеши, реальные файлы скринов и явные ограничения. Возвращает `review_receipt_valid` (квитанция структурно согласована, это **не приёмка КП**) или `draft_with_limits` с причинами; exit 2 — неполная приёмка. Он не вызывает модели или API. Непроверенные live-интеграции остаются отдельными задачами бэклога.

Формат `calculate` описан в [расчётах](calculations.md). Обновление навыков плагина после повторяемой общей ошибки — отдельная правка версии с тестом; частные предпочтения агентства остаются в его профиле.

Для полной записи замечания feedback также сохраняет `user_quote` и необязательные `source`, `before`, `after`, `proposal_sha256`, `proposal_version`, `author`, `location`, `resolution`, `recheck_result`. Они остаются в файле события для аудита и в квитанции `feedback`, но не входят в правила `context`; не пересылай файл события в другой клиентский запуск. Итоговый статус accepted назначает оркестратор только после фактического независимого вызова и смысловой проверки результата; CLI его не выдаёт.

## Дополнительные доказательства клиентского пакета (.39)

Для полного замыкания материалов принятой структуры скопируй разрешённые файлы в `client-evidence/structure/` внутри run с сохранением точных bytes. Укажи в `client-handoff.json.evidence_files` карту `run-relative client-evidence/path → sha256`. `packet` проверит каждый SHA, безопасный путь и непустой файл, скопирует его в ту же относительную позицию клиентской ревизии и включит в manifest. Это явные дополнительные материалы, не фиктивные числовые утверждения, графики или кейсы. Не включай историю, самооценку, секреты и частные профили; состав бери из разрешённого structure export. Основные доказательства должны также оставаться понятными в читаемом приложении. `bar_summary.passage_ref` копируется вместе с реальным отчётом автоматически.

Для незавершённого БАР сохрани `bar_summary.status: pending`: точные scope/type/url, `reason` из адресного `text_register.pending_items`, тот же текст причины в `limitation`, понятное `finding` и `action` из pending-row `change`. `evidence_ref` у существующей страницы — пакетная копия её сохранённого own text; у будущей — доступного peer text либо адресного source_ref pending-задачи с записанным SHA. Отчёт, вход native БАР, собственный балл и display_metric отсутствуют. Pending не становится scored или N/A и не исчезает из приложения.
Если demand_universe содержит только идентификацию сырых запросов, клиентское обоснование берётся из зафиксированного site_gap_input.demand_review: единственный кластер с теми же id, типом и status и непустыми basis/evidence. Новое авторское обоснование при сборке не подставляется вместо принятого анализа.

В .40 обязательный набор для финального пакета вычисляет workflow.client_material_refs: все разрешённые вложенные доказательства структуры, кроме самой decision_map и section_briefs_ref. Эти два файла остаются в structure-review и не передаются финальному Клиенту как объяснение замысла автора. Скопируй только полученный материальный набор в evidence_files; финальное КП и читаемое приложение должны объяснять предложение самостоятельно.
