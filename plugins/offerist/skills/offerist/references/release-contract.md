# Release contract · `decision_map` component `.34`

Release v1: when a conditional gate uses an integration action as `test_action_id`, each applicable outcome also carries `test_action_residual`: the original `estimate_ref`, nonblank `completed_work`, a list of existing `remaining_criteria`, and `scope_boundary`. Success has no remaining criteria and `original_scope_complete`; partial/failure/unavailable retain unmet original criteria with `same_estimate_original_scope`. An executed test receipt does not accept the integrated function. Explain what was tested, what remains of the initial deliverable and that this remainder stays in the same estimate line. Additional work beyond that scope requires a separate human decision; no new unit or charge is inferred. The dependent-page allocation still excludes the test action.

Both the structure packet and final client packet must include the permitted material primary evidence behind their summaries. `structure-export` follows typed source relationships, checks recorded or explicitly declared hashes and rejects missing, changed or forbidden proof. Carry this evidence into the final packet; a summary file does not replace its raw source. Arbitrary prose links and run history are not export instructions.

Before structure review, use `workflow.py scaffold --node decision_map` after its selected upstream is current. The CLI response contains a non-recordable `release_contract_scaffold` derived from selected actions, existing URL targets, source dispositions and estimate refs. Copy its `release_contract` into `decision_map.json`, then make each empty choice explicitly. The scaffold never approves a first release, a deferred action, a functional claim or future work. `record` validates declared joins; `status` confirms current state. The independent Client still checks whether material claims, affected surfaces and limited releases are substantively safe.

`release_contract` has `schema_version:3`, `first_release`, `current_release_gate`, `conditional_acceptance_paths:[]`, and `future_checkpoints:[]`. `first_release.plan_status:conditional_publishable` means the selected future package may be considered for release **after** its work and gates succeed, never that it is currently ready or published. `blocked` describes a blocker in the plan composition; `not_applicable` means there is no first-release package. All existing selected source/action/estimate/unit joins remain. Source IDs are the existing `decision_ledger.source_id` values. Unknown access and human money remain pending.

`current_release_gate` has only `status` and nonblank `reason`, for **this proposed first-release package**, not the publication history of the already-live site. Choose `untested`, `unknown`, or `blocked` for its current readiness without inventing a pending item, excluding selected future work or pretending a test ran. `not_applicable` pairs only with `first_release.plan_status:not_applicable` and no first package. It has no verified/published status or receipt field: actual release acceptance is outside this pre-sales record. The non-recordable scaffold leaves both choices blank. In the buyer-facing text, distinguish the conditionally feasible plan from this current gate in plain words.

`first_release` keeps selected B3 `included_action_ids`, `interim_acceptance`, `reason`, `interim_action_ids`, `remaining_work`, and `existing_url_actions`. The last list classifies every selected action affecting an existing canonical URL as `included`, `deferred_nonblocking` with reason, or `blocks_release` with reason, preserving all of that action's selected source IDs. A conditionally publishable plan cannot contain a declared blocking action. An interim accepted portion of one paid action goes in `interim_action_ids`; its one `remaining_work` row binds the **same** action and estimate ref to the later condition and final acceptance. It adds no unit or second charge. Do not mark a known unsafe public claim `deferred_nonblocking` merely because another work item has the same B3 phase.

Use `conditional_acceptance_paths` only when a selected diagnostic or conditional function gates another selected action. Each gate names `test_action_id`, `dependent_action_ids`, its actually selected `path_ids`, and four generic **future** outcome plans: `success`, `partial`, `failure`, `unavailable`. `partial` is a nonempty list: one existing applicable outcome row per actually offered, distinct, nonempty proper subset of declared paths; do not enumerate an unused power set. For one indivisible path use one `{ "applicability":"not_applicable", "reason":"..." }` row. An unlisted mixed subset has no preauthorized limited release and needs a separate decision. Each applicable outcome keeps `test_work_state`, `functional_state`, `publication_state`, `measurement_state`, `verified_path_ids`, `receipt_requirement`, `decision_owner`, `future_work_boundary`, and `applicability:applicable`. Success needs future executed evidence for every declared path; partial needs it for the offered subset and limits dependent claims; failure can accept executed diagnostic work but no function; unavailable accepts neither test work nor function. A limited publication or later repair/retest is a separate human decision, not automatic paid work. Do not invent a form or another path to fill the schema.

`future_checkpoints` covers B6 and B12. Each row has a unique `checkpoint_id`, `phase`, `commercial_model`, `outside_kind`, `action_ids`, `estimate_refs`, `scope`, `acceptance`, `price_boundary`. `included_work` joins selected actions in that phase exactly once to their current estimate refs; `outside_kind:null`. `outside_purchase` carries no selected actions or estimate refs; choose `outside_kind:decision_only` or `separate_option` and state the not-in-current-price boundary. A phase may have both included work and an additional outside option. Neither model assigns a provider, rate or future service without human agreement. Keep the buyer-facing B3/B6/B12 wording consistent with these rows.

For each conditional gate, declare `action_path_requirements` keyed by its exact dependent action IDs. Give each applicable outcome a `branch_allocation`: prepared, published, accepted and deferred action IDs; `remaining_criteria` keyed by deferred ID with one existing action acceptance criterion and next decision; and target, accepted and deferred quantities grouped by the action's unit. Accepted page work must be published and must have its declared paths verified. A phone-only path does not accept a page whose own stated criterion requires a received form record. A test receipt can accept the diagnostic action separately. These are future branches, not delivery or payment receipts.

In `decision_map`, add `checkpoint_deliverables` for each declared B3/B6/B12 measurement. Each row names the phase, commercial model, source/panel, period method, finite receipt, role and acceptance. Included work names the same-phase operation action and estimate ref; outside-purchase work has both refs null and requires a separate bounded decision. Add `structure_outline` with section IDs placing `SEO` immediately after `GAP`, exact `section-briefs.md` path/SHA, and one `seo_state_rows` entry for each selected audit finding. Each row names its saved source, date/status and limitation, URL/group and scale, selected action, phase and acceptance. The independent Client checks whether the saved brief and later proposal actually make these claims legible and source-supported.
